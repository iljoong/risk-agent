# 구비서류 체크리스트 모드

출력: `output\rfp-checklist-{slug}.html`.
원본대조필 필요 여부, 적용 서류, 원문 위치를 상단에 표시한다.

## 요구사항과 기준 목록의 구분

45개 이상 준비 기준을 검토하되 **RFP 요구 서류라고 자동 확정하지 않는다**.
행마다 `data-requirement="required|recommended|not-applicable|unknown"`을 표시한다.
필수는 원문 근거가 있어야 한다. 기준에만 있는 서류는 권장/확인 필요로 분류한다.
한 항목은 한 서류, 한 제출 주체, 한 단계다. 실제 대안 서류는 "또는" 관계를 보존하며
둘 다 필수인 것처럼 바꾸지 않는다. 고유명사의 구두점은 분리 근거가 아니다.

단계는 기존 표시의 3단계를 유지한다:
`registration`(사업참여등록), `bid`(입찰/제안),
`post-award`(낙찰 후 협상·계약·이행).
후자의 세부시점은 별도 설명으로 표시한다. 기존 4단계 베이스라인과 혼동하지 않는다.
총 45+ 준비 항목은 유지하되 단계별 20/5/10/10 같은 근거 없는 배분은 하지 않는다.

## 기준 카테고리

각 서류를 별도 행으로 작성한다. 조건부 항목은 적용 상태를 명시한다.

- 법인: 사업자등록증, 법인등기, 법인인감증명서, 사용인감계, 위임장,
  국세/지방세 납세증명서(각각).
- 자격: 기간통신사업자, 정보통신공사업, 전기공사업, 부가통신사업자 등록증.
- 재무: 신용평가등급확인서, 재무제표, 경영상태확인서.
- 서약: 청렴, 공정거래, 하도급대금 직불, 입찰참가자격 서약/확약서(각각).
- 입찰: 기술 제안서와 가격 입찰서(각각), 입찰보증 관련 서류, 공동수급협정서.
- 제안: 제안 요약서, 발표 자료, 평가조견표; 정량/정성 제출본이 별도면 분리.
- 인력: PM와 요구된 핵심인력별 재직/경력/4대보험 가입 증빙(각각).
  인원 수를 모르면 확인 필요로 표시하고 가상의 인물을 만들지 않는다.
- 기술/장비: 장비별 CC, 보안기능확인, KCMVP, TTA, 공급확약, 기술지원확약, 보증.
- 보안: 열람/이행 보안서약, 신원조사 동의, 보안교육 이수.
- 이행: 착수보고, 수행계획, 보안계획, 품질계획, 위험관리계획,
  SLA 월간보고, 장애보고, 검수요청, 인수인계, 하자보수계획.

## 표와 식별자

`<table id="checklist-table">` 헤더:
체크박스 / 단계 / 대표서류명 / 원문 표현 / 제출 형태 / 발급·취득 경로 /
근거 조항 / 링크 / 마감·유효기간 / 수행실적 요건 / 상태.
"담당" 컬럼은 추가하지 않는다. 마지막 컬럼은 "상태".

```html
<tr data-row data-doc-id="partner1-tax-bid" data-stage="bid"
    data-requirement="required" data-member="partner1" data-member-doc="national-tax">
  <td><input type="checkbox" class="doc-check" data-doc-id="partner1-tax-bid"
      id="chk-project-partner1-tax-bid" aria-label="구성원사 1 국세 증명 준비"></td>
  <td>입찰</td><td>국세 납세증명서</td><td>국세 납세증명서</td>
  <td>원문 확인</td><td>구성원사 수령</td>
  <td data-evidence>RFP 제3절: 원문 인용</td><td>확인 필요</td>
  <td>원문 확인</td><td>해당 없음</td>
  <td><span class="status-badge status-todo">준비 중</span></td>
</tr>
```

`data-doc-id`는 사업 내 **서류+주체+단계**를 포함해 고유화한다.
동일 서류명이라도 구성원사/장비/인력/시점이 다르면 같은 키를 쓰지 않는다.
필수가 아니어도 `data-evidence` 셀에 "표준 준비 기준 — 원문 미확인" 등 이유를 넣는다.
진행률은 `not-applicable` 행을 제외하며 해당 없음 행은 비활성 체크박스를 사용한다.

## 공동수급

`id="checklist-config"`에 `data-key="rfp-checklist-{notice-slug}"`,
`data-consortium="solo|consortium|undecided|prohibited"`를 넣는다.
단독/명시 불허면 구성원사 강제 목록은 비활성화하고 적용 전제를 표시한다.
사용자 컨소시엄 답변과 원문 불허가 충돌하면 불허 상태와 경고를 표시한다.
미정이고 명시 불허가 없으면 조건부 구성원사 준비 목록을 포함한다.
구성원 수가 불명일 때만 "구성원사 ① (미확정)" 예비 목록 한 개를 만들며
확정 구성원 수로 오인하지 않게 표시한다.

구성원별 항목(`data-member-doc`):
`registration`(입찰참가등록), `corporate-register`, `business-register`,
`credit`, `financial`, `national-tax`, `local-tax`, `insurance`,
`security-pledge`, `background-consent`, `agreement`, `share`.
기존 10항목의 묶음인 국세/지방세와 보안서약/신원조사를 분리해 **12종**으로 정정했다.
적용 여부/유효기간은 원문으로 결정한다. 공동수급협정은 실제 한 공동 문서면
중복 제출을 요구하지 않고 각 구성원사 행에 공동 문서/날인 확인임을 표시한다.
구성원 목록은 `id="consortium-members"` 안에 `data-member-id`로 선언한다.

협력업체/장비 공급/시공/하도급/보안/안전 키워드를 역방향으로 찾아 누락을 확인한다.
명시적 불허도 예외/승인 조항을 함께 검토한다.
협력업체 확약/보증/인증은 장비별 분리하되 원문 미확인은 권장 상태로 표시한다.

## 정규화, 실적, 링크

서류 매핑 자산의 대표명/유사표현/발급경로를 우선 사용한다.
매핑은 기관 양식상 법적 동등성을 보장하지 않는다. 원문 표현을 별도 보존한다.
인감증명서가 모호하면 법인인감/사용인감 두 후보를 각각 확인 필요로 남긴다.
실적은 규모/기간/서비스/건수 요건을 그대로 적고 제공된 검증 가능한 증빙만 연결한다.
관련 사업 데이터가 없으면 "실적 매핑 미확인"; 존재하지 않는 유사사업 결과에 연결하지 않는다.
사내 참고 링크 3개를 표시하되 접근 성공/최신성을 확인하지 않았다면 미검증 라벨을 넣는다.

## 상호작용

진행률 영역에 `done-count`, `total-count`, `done-pct`, `progress-bar`,
`last-updated`, `stage-progress` ID를 제공한다.
버튼 `reset-checklist`, 토글 `filter-unchecked`, 오류 영역 `checklist-error`를 제공한다.
번들 체크리스트 엔진을 인라인 삽입한다.

직접 체크/행 클릭으로 상태를 전환한다. 링크/버튼/다른 입력/라벨 클릭은 제외한다.
완료 배지/초록 행 마커/취소선/진행률/단계별 진행률을 즉시 갱신한다.
필터 중 체크 변경/해제도 즉시 반영한다.
localStorage 복원/저장 실패는 경고하며 메모리 내 체크는 계속 동작한다.
새로고침 지속성을 확인하지 못하면 검증 완료라고 하지 않는다.
